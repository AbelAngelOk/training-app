# Internacionalización del contenido de catálogo (ES/EN)

## Alcance

Esto cubre **contenido de catálogo**: nombre/descripción/instrucciones/tips de ejercicios, nombre/descripción de grupos musculares y equipo, y las etiquetas de dificultad. **No** cubre una traducción completa de los strings de UI fijos (botones, títulos de pantalla, mensajes de error, etc.) — eso es un proyecto distinto y mayor, no implementado.

El portal admin (`/admin`) **sigue siendo 100% español** en su propia UI (labels, botones, mensajes) — solo el *contenido* que carga (nombre/descripción de un ejercicio) se pide en ambos idiomas al mismo tiempo, en el mismo formulario.

## Modelo de datos

Pares de columnas `_es`/`_en` en vez de una tabla de traducciones o JSONB — más simple de consultar y tipar, adecuado al volumen del catálogo (cientos de filas, no miles).

- `exercises`: `name_es/en`, `description_es/en`, `instructions_es/en`, `tips_es/en` (todas `tips_*` NULL en 100% de los ejercicios actuales, no hay tips cargados)
- `muscle_groups`: `name_es/en`, `description_es/en` (descripción detallada, no es traducción del nombre — explica anatomía/uso)
- `equipment`: `name_es/en`, `description_es/en` (ídem)
- Relación ejercicio↔grupo muscular/equipo: muchos-a-muchos vía `exercise_muscle_groups`/`exercise_equipment` (ver `docs/DATABASE.md`)

`name_es`/`name_en` son `NOT NULL` en las 3 tablas — todo contenido de catálogo tiene que tener ambos idiomas cargados, no hay fallback a nivel de base de datos para nombres. `description_*`/`instructions_*`/`tips_*` son nullable.

## Contrato de código

- **`src/lib/i18n.ts`**: `getLocalizedText(es, en, language)` — devuelve el texto en el idioma pedido, con fallback al otro idioma si el elegido viene vacío (nunca mostrar un campo en blanco). `DIFFICULTY_LABEL: Record<AppLanguage, Record<ExerciseDifficulty, string>>`.
- **`src/hooks/use-app-language.ts`**: `useAppLanguage(): 'es' | 'en'` — detecta el idioma del dispositivo vía `expo-localization` (`getLocales()[0]?.languageCode`). Sin preferencia persistida ni pantalla de configuración: si el dispositivo no está explícitamente en inglés, se usa español por defecto.

Todo componente que muestra contenido de catálogo al usuario final llama `useAppLanguage()` una vez y pasa `language` a `getLocalizedText(...)`. Para arrays (grupos musculares de un ejercicio, que ahora son muchos-a-muchos), se resuelve cada nombre individualmente y se unen con `", "`.

## Checklist para agregar un campo bilingüe nuevo

1. Migración: agregar `campo_es`/`campo_en` (no un solo `campo`).
2. Actualizar `src/types/database.ts` (Row/Insert/Update de la tabla afectada).
3. Actualizar el `select()` de las queries en `src/api/*.ts` que traen esa tabla, pidiendo ambas columnas.
4. Si el campo se muestra en el admin: agregar los dos inputs (`Campo (Español)` / `Campo (English)`) al formulario correspondiente.
5. Si el campo se muestra en la app móvil: usar `getLocalizedText(row.campo_es, row.campo_en, useAppLanguage())` en el punto de render, nunca acceder a una sola columna directo.
6. Si hay datos existentes: escribir un backfill (ver `scripts/apply-catalog-translations.js` como referencia) antes de poner `NOT NULL` en una migración separada.

## Backfill histórico (agosto 2026)

Los 373 ejercicios + 21 grupos musculares + 13 equipos existentes al momento de esta migración se tradujeron una única vez (no hay pipeline de traducción recurrente):

- `scripts/export-catalog-for-translation.js` volcó el catálogo a `scripts/translation-work/` (gitignored).
- Las traducciones se generaron directamente (sin API de traducción externa), preservando terminología de fitness consistente entre ejercicios/grupos musculares/equipo.
- `scripts/apply-catalog-translations.js` aplicó los `UPDATE`; `scripts/verify-catalog-translations.js` confirmó 0 filas sin `name_es`/`name_en` antes de aplicar la migración que elimina las columnas legadas de un solo idioma.
